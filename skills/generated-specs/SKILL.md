# Generated specs

A spec written by hand next to the code it describes drifts from it. Give each spec one source of truth, generate every other copy from it, and make the build fail when a copy is out of date.

## What counts

Anything that states a contract the code also defines:

- API descriptions: OpenAPI, GraphQL SDL, protobuf, JSON Schema, AsyncAPI.
- Types shared across languages or between client and server.
- Database schema, ERDs and column lists.
- CLI flag and command references, config keys, environment variables.
- Error codes, event and message formats, feature-flag lists.
- Doc tables or README sections that restate any of the above.

Prose that explains why something is designed a certain way is not a spec. Write it by hand.

## Pick the source

Each spec has exactly one source, and generation runs one way only.

- **Code first** when one service owns the contract. Generate the spec from the handlers, types or migrations that run.
- **Schema first** when several languages or repositories consume it. Write the schema and generate the types and clients for each.
- Never both. A spec that is generated from code and also edited by hand has two sources.

If the code's own type is the only copy and nothing else reads the contract, there is nothing to generate. Don't add a spec file just to have one.

## Steps

1. **Inventory.** List the spec-like files and doc sections in the repo, and for each, what it restates.
2. **Choose the source** for each, using the rules above. Prefer the one that already runs in production.
3. **One command.** Wire every generator behind a single entry point the project already uses, such as `make generate`, `npm run generate` or `go generate ./...`. Pin generator versions so output is reproducible.
4. **Mark the output.** Start each generated file with the standard header its tools recognise, such as `// Code generated by <tool>. DO NOT EDIT.`, and list the paths as `linguist-generated=true` in `.gitattributes`.
5. **Drift check.** Add a CI step that regenerates and fails on any difference:

   ```sh
   make generate && git diff --exit-code && test -z "$(git status --porcelain)"
   ```

6. **Delete the hand-written copy.** Point docs at the generated file, or have the generator write the doc section between fixed markers.

## Editing

Never edit a generated file. Change its source, run the generate command and commit both together. If the generator produces something wrong, fix the generator or its input.

## Checking

Before calling a change finished, run the generate command and confirm `git diff --exit-code` is clean. In a diff, flag:

- A generated file changed without a matching change to its source.
- A new spec, schema or reference table written by hand when a source for it exists or could.
- A spec with no drift check in CI.
